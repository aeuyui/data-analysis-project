## 0. 데이터 처리 흐름

| 단계 | 스크립트 | 입력 → 출력 | 원칙 |
|---|---|---|---|
| 통합 | `00_merge_raw.py` | `data/raw/` → `data/interim/trips/` | 형식만 통일, 행 삭제 없음 |
| 점검 | `01_check_data.py` | `data/interim/trips/` → 점검 보고서 | 현황만 기록, 수정 없음 |

원본(`data/raw/`)은 어느 단계에서도 수정하지 않는다. 같은 원본과 스크립트로 다시 실행하면 같은 결과가 나온다.

## 2. 전처리 결정

각 결정은 **결정 / 근거(관찰) / 해석 / 대안 / 이후 확인** 순서로 적는다.
"관찰"은 데이터에서 확인한 사실, "해석"은 그 사실로부터의 추론이다.

### D1. 분석 기간: 2023-01-01 ~ 2025-12-31

- **결정**: 대여 시작 시각 기준으로 2023~2025년 36개월만 사용한다. 2022년 12월 자료는 제외한다.
- **관찰**: 2022년 12월 자료는 26일부터만 있고 48,901건(전체의 0.185%)이다. 다른 해 12월은 47만~56만 건이다. (`data_check_report.md` 2절, `merge_report.md` 3절)
- **해석**: 한 달의 일부만 있는 달을 포함하면 월별·계절별 비교가 왜곡된다.
- **대안**: 포함하고 "부분 월"로 표시 → 비교가 복잡해져 채택하지 않음.
- **참고**: 2025년 12월은 31일 23:59까지 있어 완전한 달이다.

### D2. 반납 정보가 없는 대여는 제외

- **결정**: 종료 일시·도착 대여소·대여 시간 중 하나라도 없는 행을 제외한다.
- **관찰**: 이 세 정보가 함께 빠진 행이 184건(0.001%)이다. (`data_check_report.md` 1절)
- **해석**: 반납이 기록되지 않은 대여로 보인다. 출발-도착 흐름(질문 2)과 대여 시간(질문 3)을 계산할 수 없다. 원인(분실, 고장 등)은 데이터로 확인할 수 없다.

### D3. 대여 시간은 `duration_ms`를 사용한다 (서머타임 문제)

- **결정**: 1회 대여 시간은 `duration_ms` 컬럼을 사용하고, (종료 시각 - 시작 시각)으로 계산하지 않는다.
- **관찰** (`data_check_report.md` 2절)
  - `duration_ms`와 (종료 - 시작)의 차이: 99.995%는 1분 이내, 나머지 1,236건은 **모두 55~65분 차이**였고 다른 구간은 0건이었다.
  - 차이가 난 날짜 상위가 2023-03-26, 2024-03-31, 2025-03-30, 2023-10-29, 2024-10-27, 2025-10-26이었다. 이 날짜는 영국 서머타임이 시작·해제되는 날(3월·10월 마지막 일요일)과 일치한다. 그 전날들도 상위에 있다.
  - 시작 시각의 초(second) 값이 모두 0이다 → 시각은 분 단위로만 기록된다.
- **해석**: 시작·종료 시각은 **영국 현지 시계 시각**이라 서머타임 전환 때 1시간 건너뛰거나 되돌아가고, `duration_ms`는 **실제 경과 시간**이다. 전날 날짜가 상위에 있는 것은 전환 시각에 걸친 긴 대여로 보인다.
- **출처 확인**: 영국 정부 안내에 따르면 시계는 3월 마지막 일요일 오전 1시에 1시간 앞당겨지고(BST 시작), 10월 마지막 일요일 오전 2시에 1시간 늦춰진다(GMT 복귀). 2025년은 3월 30일·10월 26일로 데이터의 불일치 날짜와 같다. ([GOV.UK, When do the clocks change?](https://www.gov.uk/when-do-the-clocks-change))
- **설명 포인트**: 1분 이내 차이는 시각이 분 단위로 잘려 기록되기 때문이다.

### D4. 종료 < 시작: 서머타임으로 설명되는 경우만 유지

- **결정**: 종료 시각이 시작 시각보다 빠른 행 중, 서머타임 해제일(10월 마지막 일요일)에 발생했고 차이가 60분 이내인 행은 유지하고 나머지는 제외한다.
- **관찰**: 종료 < 시작 행 185건. (`data_check_report.md` 2절)
- **결과**: **185건 모두** 서머타임 해제일(2023-10-29 48건, 2024-10-27 71건, 2025-10-26 66건)에 발생했고 시각 차이가 60분 이내였다. 제외 0건. (`preprocess_log.md` 2절, `check_tables/end_before_start_rows.csv`)
- **해석**: 해제일에는 시계가 1시간 뒤로 가므로, 그 시각에 걸친 대여는 종료 시각이 더 이르게 기록될 수 있다. 이 경우 `duration_ms`는 정상이므로 버릴 이유가 없다. 185건 전부가 이 날짜에 몰려 있다는 점이 D3의 해석(시각 = 현지 시계 시각)을 한 번 더 뒷받침한다.
- **분석 시 유의**: 이 행들은 종료 시각으로 시간대를 계산하지 않는다(분석은 시작 시각 기준).

### D5. 내용 중복은 1건만 남긴다

- **결정**: 자전거 ID, 시작 시각, 종료 시각, 출발 대여소 ID, 도착 대여소 ID가 모두 같은 행은 trip_id가 가장 작은 1건만 남긴다.
- **관찰**: trip_id는 중복이 0건이지만, 위 다섯 값이 같은 행이 463행 있다. (`data_check_report.md` 6절)
- **해석**: 같은 자전거가 같은 시각에 같은 대여소에서 두 번 출발할 수 없으므로 같은 대여가 다른 ID로 두 번 기록된 것으로 본다.

### D6. 짧은 왕복(같은 대여소, 1분 이하)은 제외

- **결정**: 출발 대여소와 도착 대여소가 같고(D8의 통일된 대여소 기준) 대여 시간이 1분 이하인 행을 제외한다.
- **관찰** (`data_check_report.md` 3절)
  - 1분 이하 대여 196,531건 중 189,903건(**약 96.6%**)이 같은 대여소 왕복이다.
  - 다른 대여소로 간 1분 이하 대여는 약 6,600건이다.
  - 종료 시각 = 시작 시각인 행이 122,587건이다(분 단위 기록이라 1분 미만 대여가 이렇게 보임).
- **해석**: 같은 대여소에서 빌려 1분 안에 같은 곳에 반납한 것은 이동이 아니라 대여 취소나 자전거 교체 같은 경우일 가능성이 크다. 원인은 데이터로 확인할 수 없으므로 "가능성"으로만 쓴다.
- **대안과 선택 이유**
  - 1분 이하 전체 제외: 다른 대여소로 간 짧은 대여(가까운 대여소 간 실제 이동 가능)까지 빠지므로 채택하지 않음.
  - 2분 이하 왕복 제외: 약 4.2만 건이 더 빠진다. 1분과 2분 중 어느 쪽이 맞는지 근거가 없어, 실제 이동일 가능성이 가장 낮은 1분 이하만 제외했다.
- **이후 확인(3차)**: 기준을 2분으로 바꿔도 결론이 같은지 민감도를 확인한다.
- **주의**: 점검 보고서의 189,903건은 원본 대여소 ID 기준이고, 전처리는 통일된 대여소 기준이라 제외 건수가 조금 다를 수 있다.

### D7. 24시간을 넘는 대여는 제외

- **결정**: 대여 시간이 24시간을 넘는 행을 제외한다.
- **관찰** (`data_check_report.md` 3절)
  - 중앙값 13.15분, 99% 지점 91.29분, **99.9% 지점 1,054.17분(약 17.6시간), 최댓값 301,435분(약 209일)**.
  - 24시간 초과 21,249건(0.081%), 3~24시간 68,542건(0.260%).
- **해석**: 하루를 넘는 대여는 한 번의 이동으로 보기 어렵다. 반납 누락이나 분실 후 회수 같은 경우일 수 있으나 데이터로 확인할 수 없다.
- **대안**: 3시간 초과까지 제외하면 약 9만 건(0.34%)이 빠진다. 24시간은 설명하기 쉬운 경계여서 선택했다.
- **분석 시 유의**: 남은 데이터도 꼬리가 길어 평균이 끌려간다. 질문 3은 중앙값과 분위수 중심으로 본다.
- **이후 확인(3차)**: 기준을 3시간으로 바꿔도 결론이 같은지 확인한다.

### D8. 대여소는 정리된 이름(station_key)으로 통일한다

- **결정**: 분석 단위를 원본 대여소 ID가 아니라, 아래 규칙으로 만든 `station_key`로 한다.
  - A. 이름 표기 정리: 공백 정리, 쉼표 앞 공백 제거 (예: `Kennington Road  , Vauxhall` → `Kennington Road, Vauxhall`)
  - B. 같은 ID 안의 표기 변형 통일: 같은 ID에서 가장 많이 쓰인 이름과 유사도 0.9 이상이면 그 이름으로 (예: `St. Lke's` → `St. Luke's`)
  - C. 정리된 이름이 같으면 ID가 달라도 같은 대여소로 본다.
  - D. 같은 ID의 다른 이름이 **같은 지역(쉼표 뒤 지역명)**이고 **동시에 쓰인 달이 3개월 미만**이면 이름 변경으로 보고 통합한다 (예: `Bayley Street, Bloomsbury` ↔ `Percy Street, Bloomsbury`). 지역이 다르면 ID 재사용으로 보고 분리한다 (예: `Clapham South` ↔ `Coomer Place, West Kensington`). 같은 지역이어도 오래 동시에 쓰였으면 분리한다.
  - 통합된 이름 묶음은 가장 많이 쓰인 이름을 `station_key`로 쓴다.
- **관찰** (`data_check_report.md` 4절)
  - 대여소 ID 1,252개, 이름 845개.
  - **ID가 2개 이상인 이름이 423개**, 이름이 2개 이상인 ID가 16개.
  - ID 형태가 `000964`, `200025`처럼 두 가지이고, `001057_old` 같은 숫자가 아닌 ID도 2개 있다.
- **해석**: 이름의 절반가량이 여러 ID를 가진 것은 개별 오류보다는 **기간 중 ID 체계가 바뀌었을 가능성**을 시사한다. 이를 ID 그대로 분석하면 같은 대여소가 둘로 쪼개져 질문 1(대여소 유형)과 질문 2(흐름, 불균형)가 왜곡된다.
- **검증 장치**: 같은 이름의 여러 ID가 **같은 달에 함께 쓰였는지**를 센다(한 달 30건 이상만 "사용 중"으로 봄).
  - ID 체계 변경이라면 옛 ID가 끝날 무렵 새 ID가 시작되므로 함께 쓰인 달이 거의 없어야 한다.
  - 3개월 이상 함께 쓰였다면 이름만 같은 다른 대여소일 수 있어 검토 대상으로 표시한다.
  - 결과: `preprocess_log.md` 3절, `check_tables/station_key_summary.csv`의 `shared_months`, `review_needed`.
- **결과 (1차 실행, 규칙 A~C)** (`preprocess_log.md` 3절)
  - 원본 (ID, 이름) 쌍 1,268개 → 대여소 840개.
  - ID 2개 이상이 합쳐진 대여소 422개 중 **419개는 여러 ID가 같은 달에 함께 쓰인 적이 0개월, 3개는 1개월**이었다.
  - 처음 해석: "옛 ID가 끝나는 달에 새 ID가 시작되었으므로 ID 체계가 바뀌었다."
- **해석 정정 (2차 실행)**
  - 앞자리 0을 무시하고 세면 원본 ID 1,252개는 **833개**가 되고, **같은 번호가 `000964`/`964`처럼 두 형태로 모두 나타나는 경우가 419개**였다.
  - 즉 "여러 ID"의 대부분은 **새 번호로 바뀐 것이 아니라 같은 번호의 표기 형식(앞자리 0)이 시기에 따라 달라진 것**으로 보인다. "ID 체계 변경"은 과장된 표현이므로 "**ID 표기 형식 변경**"으로 고친다.
  - 최종 실행 로그에서 직접 세어 확인: 여러 ID가 합쳐진 대여소 422개 중 **419개가 앞자리 0 차이만으로 설명**된다.
  - 시사점: ID의 앞자리 0만 정리하면 ID가 대여소를 거의 일대일로 식별한다. 이름 기준 통일(규칙 C)과 결과는 거의 같지만, 보고서에서는 "이름 기준으로 통일했고, ID 기준으로도 교차 확인했다"고 설명할 수 있다.
  - 규칙 B로 통일된 5건: 오타(`St. Lke's`), 번호 추가(`Concert Hall Approach` → `Concert Hall Approach 2`), `_OLD` 접미사 2건. 모두 같은 ID 안의 변화라 같은 대여소로 보는 것이 타당하다고 판단했다.
- **규칙 D를 추가한 이유 (1차 실행 결과 검토)**
  - 1차 실행에서 "같은 ID인데 이름이 달라 분리"된 10건을 보니, 다수가 **같은 동네에서 이름만 바뀐 경우**였다: `Bayley`→`Percy Street`(Bloomsbury), `Earnshaw`→`Bucknall Street`(Covent Garden), `Parkway`→`Albert Street`(Camden Town), `Argyle`↔`Belgrove Street`(King's Cross), `Fore Street`↔`Fore Street Avenue`(Guildhall, 두 ID가 서로의 이름을 함께 가짐), `London Fields, Hackney`↔`Hackney Central`.
  - 이들을 분리하면 한 대여소가 시기별로 둘로 쪼개져 3년 이용량 순위나 출발·도착 불균형(질문 2)이 왜곡된다.
  - 반대로 `Coomer Place, West Kensington`↔`Clapham South`, `Adeline Place, Bloomsbury`↔`Abyssinia Close, Clapham Junction`, `Agar Grove, Camden Town`↔`Concert Hall Approach 1, South Bank`는 **지역이 달라** ID 재사용으로 보고 분리를 유지한다.
  - 철자 유사도(규칙 B)는 오타만 잡고 이름 변경은 못 잡는다는 한계가 있어, 지역명과 사용 시기를 함께 보는 규칙을 추가했다.
- **규칙 D 적용 결과 (2차 실행)**: 7건 통합, 3건 분리(다른 지역). 대여소 840개 → 834개. 짧은 왕복 제외는 189,287 → 189,310건(+23)으로, 합쳐진 대여소의 출발·도착이 같아진 영향이다.
- **안전장치가 잡아낸 잘못된 통합: Fore Street** (2차 실행 → 규칙 보완)
  - 관찰: 규칙 D가 `Fore Street, Guildhall`(ID 300222)과 `Fore Street Avenue, Guildhall`(ID 200253)을 하나로 합쳤는데, 대여소 요약의 "함께 쓰인 달" 검사에서 **두 ID가 37개월(전 기간) 동시에 운영**된 것으로 나와 검토 대상으로 표시되었다.
  - 해석: 두 ID는 3년 내내 함께 운영된 **서로 다른 두 대여소**이고, 약 1개월 동안 두 ID의 이름이 서로 뒤바뀌어 기록되었다. 각 ID의 "다른 이름"은 이름 변경이 아니라 옆 대여소의 이름이었다.
  - 보완: "다른 이름이 같은 기간(3개월 이상) 운영 중인 다른 ID의 대표 이름이면 통합하지 않는다"는 조건을 규칙 D에 추가했다.
  - 이름이 뒤바뀐 약 1개월의 기록(원본 기준 출발·도착 합산 약 1.5만 건, 0.03% 수준)은 원칙 C에 따라 **기록된 이름 기준**으로 배정된다. 이름과 ID 중 어느 쪽이 잘못 기록됐는지는 확인할 수 없으며, 원칙의 일관성을 위해 이름을 따랐다. 영향은 작다.
- **좌표가 없어서 생기는 한계**: 이름이 바뀐 대여소가 같은 자리인지, 같은 동네 안에서 옮겨간 것인지 확인할 수 없다. 같은 동네 안의 이전은 대여소의 역할이 크게 다르지 않다고 보고 통합했다. 이는 **가정**이며 보고서의 한계에 적는다.
- **검토할 것**: `check_tables/station_rename_checks.csv`의 판정(특히 "통합"), `station_mapping.csv`의 `B_표기변형통일` 행.

- **근거**: 자전거 ID는 분석 질문에 쓰지 않고, 다른 값은 정상이다. (`data_check_report.md` 1절)

### D10. 자전거 모델 비교는 연도를 나눠서 한다 (분석 시 유의)

## 5. 예상 질문과 답변 (발표·보고서 대비)

**Q. 왜 Kaggle 데이터 대신 원데이터를 썼나?**
1개월 자료의 한계(계절 변화 확인 불가, 일반화 어려움)를 줄이려고 원 출처에서 3년치를 확보했다. 원데이터의 2023년 8월 행 수가 Kaggle과 같아 사본과 원본이 일치함을 확인했다.

**Q. 대여 시간을 왜 종료 - 시작으로 계산하지 않았나?**
두 값의 차이가 서머타임 전환일에만 정확히 60분 나는 것을 확인했다. 시각은 현지 시계 시각이고 `duration_ms`는 실제 경과 시간이라고 판단했다.

**Q. 1분 이하 대여를 다 빼지 않고 왕복만 뺀 이유는?**
1분 이하 대여의 약 96.6%가 같은 대여소 왕복이라 이동이 아닐 가능성이 크다. 다른 대여소로 간 짧은 대여는 가까운 대여소 사이의 실제 이동일 수 있어 남겼다.

**Q. 24시간 기준은 근거가 있나?**
정해진 정답은 없다. 하루를 넘는 대여는 한 번의 이동으로 보기 어렵다는 판단이고, 제외 비율은 0.081%로 작다. 3시간 기준으로 바꿔도 결론이 같은지 3차에서 확인한다.

**Q. 대여소 ID를 그대로 쓰지 않은 이유는?**
이름 845개에 ID가 1,252개였는데, 앞자리 0을 무시하면 ID는 833개였다. 같은 번호가 `000964`와 `964` 두 형태로 모두 나타나는 경우가 419개로, 시기에 따라 ID 표기 형식이 달라진 것으로 보인다. ID 그대로 쓰면 같은 대여소가 둘로 쪼개지므로 이름 기준으로 통일했다. 같은 이름의 ID들이 같은 달에 함께 쓰이지 않았다는 점(422개 중 419개가 0개월)도 확인했다.

**Q. 통일 규칙이 잘못 합친 경우는 없나?**
있었다. Fore Street와 Fore Street Avenue가 이름 변경 규칙으로 합쳐졌는데, 두 ID가 3년 내내 동시에 운영된 것을 검사로 발견했다. 한 달 동안 이름이 뒤바뀌어 기록된 서로 다른 대여소였다. 규칙에 "운영 중인 다른 대여소의 이름이면 합치지 않는다"는 조건을 추가해 분리했다.

**Q. 이름이 다른데 같은 대여소로 합친 근거는?**
같은 ID 안에서 지역명이 같고 두 이름이 동시에 쓰이지 않은(한쪽이 끝난 뒤 다른 쪽이 시작된) 경우만 이름 변경으로 봤다. 지역이 다르면 ID 재사용으로 보고 분리했다. 좌표가 없어 같은 동네 안의 이전 여부는 확인할 수 없다는 한계가 있다.

**Q. 종료 시각이 시작보다 빠른 데이터는 어떻게 했나?**
185건 모두 서머타임 해제일에 발생했다. 대여 시간(`duration_ms`)은 정상이라 모두 유지했다.

**Q. 전처리로 데이터가 얼마나 줄었나?**
약 26.39백만 행에서 약 26.13백만 행으로, 전체의 약 0.98%가 빠졌다. 가장 큰 항목은 짧은 왕복(0.717%)과 2022년 12월 부분 월(0.185%)이다.
